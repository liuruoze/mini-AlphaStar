## 三、RL 稳定性与性能（rl，8 个提交）

**六号僵死（soak#6）**

- **仍未定位**。累计约 11 小时 soak 未复现；
- 修掉一条**真实的死锁**：tensorboard 写盘线程死亡后，第 11 条曲线会把参数服务永久阻塞
  （故障注入证明，栈停在 `queues.py:83 in put`）；但它的签名与 #6 不符；
- 最可能形态：batch server 卡在 CUDA 调用（机器有 `Xid 43` 记录）。代码层修不掉，改为**让它可见**：
  两段式看门狗（300 s dump / 600 s 终止）、actor 超时 180 s、RSS 守卫 40 GB、每轮 Xid 记录、SIGUSR1。

**两个隐性缺陷**

- 护栏的有效性判据用错属性（`_event_queue` 而非 `_worker`），不一致时**静默失效**；
- Worker 的 `SummaryWriter` 从不关闭，每条日志留一条 `EOFError` Traceback。

**性能**

- 剖析显示每轮 14.4 ms 花在"通知 actor"上——`mp.Event` 在 CPython 里是 Condition 锁；
- 改用 `Semaphore`：通知 **14.4 ms → 0.08 ms**，每轮 **99 → 70 ms**，
  稳态 **84 → 101 step/s（+20%）**；长跑 2 小时 23 分零故障。

## 六、已知限制（摘要）

- 六号僵死未定位，复发时预期有 `[stall]` 行与全线程栈；若看门狗未触发，说明是另一条路径；
- `fork` 启动方式在 CUDA 下不可用（`Cannot re-initialize CUDA in forked subprocess`），spawn 必须保留；
- 每进程 RSS 实测 3.9 GB，15×2 配置合计约 78 GB。
